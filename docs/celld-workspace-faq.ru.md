# celld: Worker, workspace, SQLite и S3 — вопросы и ответы

Конспект обсуждения по коду и документации текущего checkout репозитория.
Пример приложения находится в [`examples/workspace`](../examples/workspace/README.md).
Описанные гарантии предполагают хранилище, выполняющее требования celld к
условным записям и согласованности; одной декларации «S3-compatible» недостаточно.

## Вопрос: какие API предоставляет celld после запуска с S3?

**Ответ.** celld — среда исполнения приложений, совместимых с частью платформы
Cloudflare Workers. S3 хранит deployments, состояние объектов, записи владения,
leases и данные R2. Запуск celld с пустым бакетом ещё не создаёт прикладной API:
узел ожидает первый deployment.

API разделены на три уровня:

| Уровень | Что доступно |
| --- | --- |
| Публичный HTTP-вход, `--listen` | `/.well-known/celld/health`; остальные пути обслуживает ваш Worker или static assets |
| API внутри Worker | Durable Objects, KV, D1, R2, Queues, Workflows, Cron Triggers, service bindings и runtime API |
| Внутренний HTTP-вход, `--internal-listen` | Управление узлом, диагностика, обращения к объектам и межузловой протокол |

Внутри Worker доступны, например, KV `get/put/delete/list`, SQL через D1,
объектное хранилище через R2, очереди и Durable Objects с SQLite, транзакциями,
alarms и WebSocket. Ресурсы объявляются bindings в конфигурации приложения.
Также поддерживаются Dynamic Workers и Durable Object Facets; Containers
экспериментальны, совместимость с Node.js частичная.

Подключение S3 не создаёт публичные `/kv`, `/sql` или `/queue`. celld не
предоставляет S3-совместимый endpoint, публичные URL R2 или presigned URLs.
Cloudflare REST API для D1, Queues и Workflows тоже не реализованы. Внешний
HTTP-доступ к нужным операциям следует реализовать в Worker.

Основные внутренние маршруты:

| Путь | Назначение |
| --- | --- |
| `/state` | Состояние узла и счётчики |
| `/cell/<SCOPE>` | Определить владельца или активировать cell |
| `/evict/<SCOPE>` | Попытаться выгрузить cell |
| `/do/<ID>` | Прямой запрос к обычному Durable Object |
| `POST /reload` | Подхватить deployment на этом узле |
| `POST /rebalance/pause`, `POST /rebalance/resume` | Управление балансировкой |
| `POST /shutdown` | Корректная остановка и передача владения |
| `/runtime/<SCOPE>` | HMAC-аутентифицированные запросы к зарезервированным runtime-классам |
| `/peer/*` | Межузловые вызовы, диагностика и репликация |

Большинство операторских маршрутов не аутентифицирует клиента. Внутренний порт
должен быть доступен только доверенным узлам и операторам. celld сам не завершает
TLS. Для администрирования также есть команды `celld d1`, `kv`, `r2`, `queue`,
`cell list` и `diagnose`.

Источники: [совместимость](cloudflare-compat.md), [безопасность](security.md),
[R2](services/r2.md).

## Вопрос: как загрузить собственный Worker?

**Ответ.** Команда `celld deploy` собирает проект и записывает его напрямую в
бакет fleet. Её можно запускать локально или из CI; подключаться к HTTP-порту
работающего celld для публикации не требуется. Нужны CLI `celld`, `esbuild`
в `PATH` и credentials для того же бакета и префикса, которые используют узлы.

Минимальная конфигурация `wrangler.jsonc`:

```json
{
  "name": "my-worker",
  "main": "index.js",
  "compatibility_date": "2026-01-01"
}
```

Минимальный `index.js`:

```js
export default {
  async fetch(request) {
    return Response.json({ path: new URL(request.url).pathname });
  }
};
```

Публикация из каталога проекта:

```sh
celld deploy . --bucket s3://my-celld-bucket
```

Для другого S3-совместимого провайдера при необходимости добавляются
`--endpoint URL --region REGION`. Credentials берутся из стандартной AWS
credential chain. Поддерживаются `wrangler.json` и `wrangler.jsonc`, но не
`wrangler.toml`; неподдерживаемые ключи, в том числе `routes`, отклоняются.

Узлы проверяют `deploy/current.json` раз в 30 секунд по умолчанию и применяют
обновление без перезапуска процесса. `POST /reload` на внутреннем порту
конкретного узла запускает подхват немедленно. Новые версии публикуются повторным
`celld deploy`. `--dry-run` проверяет сборку без записи в бакет.

Для локальной разработки без S3:

```sh
celld dev .
```

По умолчанию приложение доступно на `http://127.0.0.1:9876`.

Источник: [деплой и обновление приложения](README.md#deploy-an-application).

## Вопрос: как устроен написанный пример workspace с версиями файлов?

**Ответ.** Один `workspaceId` адресует один Durable Object класса `Workspace`.
Все файлы workspace и их история находятся в SQLite-базе этого объекта.
`filename` — логический ключ, а не путь на файловой системе pod.

Запись выполняется через `PUT /files`:

```json
{
  "workspaceId": "demo",
  "filename": "src/main.js",
  "content": "console.log(1);",
  "currentVersion": 0
}
```

Версии считаются **отдельно для каждого файла**. Отсутствующий файл имеет
условную версию `0`. Успешная запись добавляет новую строку с полным контентом и
версией `currentVersion + 1`, даже если контент не изменился. Старые строки
сохраняются. Схема таблицы:

```sql
CREATE TABLE IF NOT EXISTS file_versions (
  filename TEXT NOT NULL,
  version INTEGER NOT NULL CHECK (version > 0),
  content TEXT NOT NULL,
  PRIMARY KEY (filename, version)
);
```

При успехе возвращается HTTP 200 и `{workspaceId, filename, version}`. При
несовпадении ожидаемой версии — HTTP 409 и фактическая `currentVersion`, без
добавления строки. Пустой контент допустим. Входная версия должна быть целым
неотрицательным безопасным JavaScript-числом меньше `Number.MAX_SAFE_INTEGER`.

Чтение последней и исторической версии:

```text
GET /files?workspaceId=demo&filename=src%2Fmain.js
GET /files?workspaceId=demo&filename=src%2Fmain.js&version=1
```

Ответ содержит `workspaceId`, `filename`, `version`, `content`. Отсутствующий
файл или версия дают 404, некорректный ввод — 400. В примере нет авторизации
workspace, удаления истории или дедупликации по ID запроса.

Файлы примера: [Worker](../examples/workspace/index.js),
[конфигурация](../examples/workspace/wrangler.jsonc),
[инструкция](../examples/workspace/README.md).

## Вопрос: означает ли один workspace один SQLite-файл в S3?

**Ответ.** Один workspace соответствует одной логической SQLite-базе, но
**не одному S3-объекту `workspace.sqlite`**.

На узле-владельце celld работает с локальной SQLite-базой. Её изменения
реплицируются в формате LTX. Данные в бакете находятся под префиксами вида
`cells/<cell>/ltx/e<epoch>/`; часть данных может сначала попадать в общие
журнальные bundles. Восстановление собирает нужное состояние из этих данных.

Если требуется ровно один скачиваемый `.sqlite` на workspace, нужен отдельный
механизм snapshot/export. Наш пример использует штатную репликацию celld и
такой экспорт не реализует.

Источники: [Durable Objects](services/durable-objects.md),
[гарантии и восстановление](guarantees.md).

## Вопрос: могут ли два параллельных запроса сохранить разный контент под одной версией?

**Ответ.** В нашем примере при нормальной работе celld один запрос успешно
сохранит новую версию, второй получит 409. Сравнение версии и `INSERT` выполняются
внутри `storage.transactionSync()`, без `await` между чтением и записью.
Синхронные участки одного Durable Object не выполняются одновременно.

Например, оба запроса ожидают версию `5`:

1. Запрос A читает `5`, вставляет `6` и завершает транзакцию.
2. Запрос B читает уже `6`, сравнивает с ожидаемой `5` и возвращает 409.
3. Строка от B не добавляется, контент A не перезаписывается.

Порядок победы не гарантирован. Важна атомарность сравнения и записи, а не
порядок прихода HTTP-запросов. Задержка S3 не открывает окно гонки: следующий
запрос читает актуальную локальную SQLite-базу, а не скачивает отдельную старую
копию из бакета. Запросы с разных узлов направляются одному владельцу объекта.

Если ответ потерялся после коммита, повтор с прежней версией тоже получит 409.
Клиент должен прочитать актуальный контент и разрешить конфликт. Ошибка или
таймаут сами по себе не доказывают, что запись не произошла.

Источник: [реализация CAS](../examples/workspace/index.js).

## Вопрос: как celld маршрутизирует запросы при round-robin между Kubernetes pod’ами?

**Ответ.** Round-robin для публичных запросов подходит; sticky sessions не
нужны. Worker выполняется на узле, который получил запрос. При обращении через
binding к Durable Object celld находит владельца и выполняет вызов локально
или пересылает его на внутренний адрес владельца.

Пример: workspace находится на pod B, а запрос пришёл на pod A:

```text
Клиент → балансировщик → pod A:8080 → Worker
                                      ↓ binding.fetch()
                                   pod B:8081 → Workspace → SQLite
                                      ↓ ответ
Клиент ← балансировщик ← pod A ←───────┘
```

Ответ возвращается через исходный pod. Клиентский HTTP redirect не требуется.
Межузловые вызовы используют HTTP-туннель `/peer/tunnel`; соединения
переиспользуются. За удалённый вызов платим дополнительным сетевым переходом.

Для каждого pod нужны отдельные настройки:

```text
--listen 0.0.0.0:8080
--internal-listen 0.0.0.0:8081
--advertise <IP-этого-pod>:8081
```

IP можно получить через Kubernetes Downward API (`status.podIP`). Публичный
Service направляет трафик на 8080; pod’ы должны иметь прямой доступ к адресам
друг друга на 8081. NetworkPolicy должна разрешать этот обмен.

**Общий балансируемый Service нельзя использовать как `--advertise` всех
узлов:** обращение к конкретному владельцу тогда попадёт на случайный pod.
Если доступен только общий round-robin endpoint и нет возможности адресовать
отдельный узел, штатная маршрутизация celld работать не сможет.

Источники: [путь запроса](services/workers.md#the-request-path),
[настройка узлов](README.md#add-nodes),
[Kubernetes Downward API](https://kubernetes.io/docs/tasks/inject-data-application/environment-variable-expose-pod-information/).

## Вопрос: где и как фиксируется владение Durable Object?

**Ответ.** celld хранит запись `cells/<cell>/own.json` с идентификатором узла
и поколением владения:

```json
{"node":"node-session-id","epoch":7}
```

Если записи нет, узел делает условное создание: оно должно пройти только при
отсутствии объекта. Если несколько узлов одновременно претендуют на cell,
победит один. Изменение существующей записи выполняется через CAS с проверкой
её ETag. При активации или смене владельца увеличивается `epoch`.

Отдельная запись `nodes/<node>.json` содержит адрес узла и срок действия его
lease. Узел продлевает lease; остальные используют его для проверки живости
владельца. Истечение lease позволяет запустить процедуру перехвата владения.

`epoch` участвует в префиксе репликации. Старый владелец может физически
продолжать запись в старый префикс, но не получает права изменять новое поколение
или подтверждать устаревшие записи как действующий владелец.

Здесь два независимых механизма CAS: **в S3 — за владение workspace**, а
**в SQLite — за версию файла**. `epoch` не равен `currentVersion` и не
увеличивается на каждое обновление файла.

Источники: [механизм владения](guarantees.md#the-mechanism),
[реализация ownership-record](../crates/celld/ownership_store.rs).

## Вопрос: в какой момент создаются Workspace и его SQLite-база?

**Ответ.** В примере обращение выглядит так:

```js
env.WORKSPACES.getByName(input.workspaceId).fetch(request);
```

Последовательность для нового workspace:

1. Внешний Worker валидирует входные данные.
2. `getByName()` вычисляет стабильный ID и возвращает stub; само получение
   stub ещё не создаёт работающий объект и базу.
3. `.fetch()` инициирует обращение. celld определяет или захватывает владение.
4. Узел-владелец подготавливает SQLite: открывает новую базу либо восстанавливает
   существующую. Локальный путь имеет вид
   `<data_dir>/<cell>/ltx/e<epoch>/db.sqlite`.
5. Рантайм создаёт экземпляр `Workspace`; конструктор выполняет
   `CREATE TABLE IF NOT EXISTS file_versions`.
6. `Workspace.fetch()` читает или обновляет файл.
7. Перед успешным ответом на запись celld обеспечивает её долговечность
   согласно выбранному режиму.

Есть два следствия: валидный `GET` неизвестного workspace создаст пустой объект
и вернёт 404; первый `PUT` с неверной ожидаемой версией может создать пустой
workspace, но не версию файла. Невалидный ввод отклоняется до активации.

После выгрузки объекта из памяти его данные сохраняются. При следующей
активации конструктор вызывается заново, а `IF NOT EXISTS` сохраняет таблицу и
историю. Имя Worker и класса следует сохранять стабильными: их изменение
меняет namespace/идентичность объектов.

Источники: [код примера](../examples/workspace/index.js),
[активация рантайма](../crates/celld/runtime.rs),
[идентичность Durable Objects](services/durable-objects.md#identity-and-addressing).

## Вопрос: все ли базы, которыми владеет pod, постоянно хранятся на его диске?

**Ответ.** Не обязательно целиком и не обязательно постоянно. Активная cell
использует локальную SQLite-базу. Большая восстанавливаемая база может сначала
быть разреженным файлом: страницы подгружаются из S3 при обращении, остальное
заполняется в фоне. Неактивный объект может сохранять владение, даже если его
локальная копия уже удалена из кэша или ещё не восстановлена на этом узле.

На диске также находятся WAL, данные репликации, кэш неактивных баз и журналы,
которые узел хранит в роли follower для других узлов. Следовательно, требуемое
место не равно только сумме SQLite-файлов своих активных workspace.

`CELLD_LOCAL_CACHE_MAX_BYTES` ограничивает кэш выгруженных SQLite-баз; значение
по умолчанию — 2 GiB. **Это не общий лимит дискового пространства celld**:
активные базы и журналы репликации этим параметром не ограничиваются.

Источники: [восстановление](guarantees.md#epoch-chain-restore),
[параметры CLI](../crates/celld/main/cli.rs),
[очистка локального кэша](../crates/celld/replication.rs).

## Вопрос: что произойдёт, если на диске pod закончится место?

**Ответ.** Новый объект может не пройти создание или восстановление базы;
запись в существующий — завершиться ошибкой SQLite, например `SQLITE_FULL`.
Ошибка локального журнала также может помешать репликации и подтверждению
долговечности. Точный исход зависит от этапа, на котором произошёл сбой.

В нашем Worker ошибки хранилища не перехватываются и обычно приводят к HTTP 500.
HTTP 409 предназначен только для CAS-конфликта. Рантайм учитывает критические
ошибки SQLite и запрещает успешный ответ при нарушенном состоянии транзакции.
При ошибке после локального коммита результат запроса может быть неопределённым
для клиента; перед повтором нужно проверить актуальное состояние.

В проверенном коде не найден механизм автоматической миграции workspace
именно по недостатку свободного дискового пространства. Разгрузка по памяти
и числу объектов не заменяет такой механизм. Неудачная активация может оставить
владение за тем же узлом, поэтому повтор запроса способен снова попасть на
переполненный диск.

Практически нужны мониторинг места, запас под активные базы и журналы,
увеличение тома либо контролируемая передача объектов. Нельзя вручную удалять
живые базы или журналы как «кэш»: они могут содержать ещё не загруженные данные.
В нашем примере хранится полный контент каждой версии без политики удаления,
поэтому объём истории постоянно растёт.

Источники: [обработка ошибок SQLite](../crates/logic/sqlite.rs),
[состояния после неудачной активации](../crates/logic/lib.rs),
[разгрузка по памяти](../crates/logic/pressure.rs).

## Вопрос: что происходит при удалении pod и создании нового с другим IP?

**Ответ.** Сам по себе новый IP не меняет идентичность workspace. При обычном
запуске celld генерирует новый идентификатор сессии и публикует свой новый
`--advertise`. Все узлы продолжают использовать общий бакет и префикс.

При корректной остановке SIGTERM celld перестаёт принимать новые запросы,
завершает или передаёт работу, обеспечивает долговечность данных и передаёт
владение. При аварийной остановке остальные узлы дожидаются истечения lease
старого владельца, захватывают объекты с новым `epoch` и восстанавливают их.
Lease по умолчанию — 10 секунд, но это не обещание восстановления за 10 секунд:
восстановление журналов и больших баз может занять существенно дольше.

Новый pod не обязан получить тот же набор workspace. Во время смены владельца
возможны задержки и ошибки запросов. Уже отправленный запрос с неопределённым
результатом нельзя считать безопасным для автоматического повторного выполнения.

Для корректной остановки `terminationGracePeriodSeconds` должен превышать
`CELLD_SHUTDOWN_TOTAL_MS` — по умолчанию 40 секунд. Стандартные 30 секунд
Kubernetes меньше этого бюджета. Доступность восстановленных данных также
зависит от того, сохранились ли необходимые локальные реплики и доступны ли они.

Источники: [shutdown и rollout](README.md#shut-down-and-roll-out-a-node),
[истечение lease](guarantees.md#self-fencing),
[жизненный цикл Pod](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/).

## Вопрос: можно ли считать локальные диски полностью одноразовыми, раз есть S3?

**Ответ.** Это зависит от режима долговечности:

| Режим | Что означает успешный ответ на запись |
| --- | --- |
| `CELLD_DURABILITY=bucket` | Запись уже подтверждена объектным хранилищем |
| `CELLD_DURABILITY=fleet`, по умолчанию | Запись уже в бакете либо подтверждена дисками followers; загрузка в бакет может ещё продолжаться |

Один узел без followers в любом случае ждёт бакет. Несколько узлов в режиме
`fleet` могут отвечать быстрее благодаря подтверждению на дисках соседей.
При потере владельца celld собирает незагруженный журнал с сохранившихся
followers перед восстановлением объекта.

**Гарантия сохранности подтверждённых записей не покрывает уничтожение всех
их копий до загрузки в S3.** Если вместе с владельцем потерять диски всех
followers, хранящих соответствующие записи, возможна потеря данных. Недоступность
необходимых реплик также может блокировать восстановление. В коде есть механизм
фиксации обнаруженной невосстановимой потери в `loss.json`.

Для инфраструктуры, в которой pod’ы и их диски должны свободно пересоздаваться,
режим `bucket` даёт понятную границу: успешный ответ означает наличие записи
в S3. Цена — ожидание объектного хранилища на каждой записи. Это не отменяет
потребность в достаточном локальном диске во время работы.

Для режима `fleet` с низкой задержкой записи следует обеспечить сохранность
томов с `CELLD_WATCH` и доступность реплик при восстановлении. Постоянные тома
снижают риск потери данных при пересоздании pod, но не защищают от уничтожения
всех реплик. `emptyDir` удаляется вместе с pod; жизненный цикл PersistentVolume
не зависит от конкретного pod, хотя удаление PVC/PV и политика reclaim требуют
отдельного внимания.

## Вопрос: что уже проверено в примере, а что пока не проверялось?

**Ответ.** В ходе работы прошли пять тестов обработчиков и SQL на настоящем
SQLite через Node.js с адаптером API хоста Durable Object. Они проверяют:

- создание workspace и сохранение истории при повторном создании экземпляра;
- конкурентное создание и обновление: из 12 запросов с одной ожидаемой версией
  проходит ровно один, остальные получают 409;
- отсутствие записи при CAS-конфликте, включая отсутствующий файл;
- изоляцию workspace и независимые версии разных файлов;
- отклонение некорректных запросов до активации объекта.

Запуск из корня репозитория:

```sh
npm --prefix examples/workspace test
```

Тесты не запускали настоящий celld, Kubernetes, репликацию в S3, переполнение
диска или восстановление после падения узлов. Описание этих механизмов основано
на изучении кода и документации проекта, а не на проведённом эксплуатационном
испытании. Сам пример не публиковался в S3.

Источник: [тесты примера](../examples/workspace/index.test.mjs).
